# OpenCredit lead ingestion foundation

Scope: receive `lead.assigned` contract version 2. This does not start attendance,
create Conversation/Message, send WhatsApp, call AI, credit APIs or feedback.

## Binding and authentication

POST `/api/integrations/opencredit/webhooks/{publicWebhookId}` resolves a persisted
OpenCreditIntegration. Company comes exclusively from this binding, never JSON.
New integrations default to disabled. The public ID is 24 random bytes in hex,
generated by `createOpenCreditPublicWebhookId`; it is not authentication.

`prepareOpenCreditWebhookSecret` uses the existing AES-256-GCM envelope and
QEVORA_DATA_ENCRYPTION_KEY_V1 infrastructure. Plaintext storage/read fallback is
not supported. HMAC-SHA256 authenticates the exact raw bytes, via
`X-CreditCore-Sig: sha256=<hex>`, using timing-safe comparison. Missing secret,
key, signature, disabled or unknown integration fail closed.

No management UI/API or production configuration is added in this PR. Controlled
onboarding, provisioning of the binding and supplier URL registration remain a
separate authorized operation. Do not expose configuration rows through DTOs.

## Persistence and contact policy

OpenCreditEvent is unique by integrationId/eventId. OpenCreditLead is unique by
companyId/integrationId/externalLeadId; lead.id remains the external identifier.
Composite foreign keys enforce company isolation, including the optional Contact.
The event, external identity and new Contact commit in one serializable transaction.
P2034 and identified event/lead P2002 recovery is bounded to three attempts.
P2002 with missing/unknown target or a different model fails closed, without retry
or successful acknowledgement. Failed transactions roll back.
Committed duplicates return 200; conflicting reuse of eventId returns 409.

Contact lookup uses the shared phone identity helper with company scope and no
alternate-number inference. Duplicate CPF/phone and legacy phone ambiguity are
recorded as NEEDS_REVIEW, without changing contacts. Existing contacts are preserved,
including trusted fields, ownership, stage, archive state and history. New contacts
require a valid phone; optional CPF/name/email are used, with a neutral name if absent.
An explicit foreign DDI (`+1`, `+351`, etc.) is not passed to BR normalization:
phone becomes unusable/null, the external lead is retained, and CPF-only identity
resolution remains possible. Local BR and valid `+55` numbers use the existing
normalizer unchanged. Impossible assignedAt calendar dates are rejected; valid
RFC3339 Z/offset timestamps are accepted.
Existing OpenCredit Origin and first tenant stage are used if present; no metadata
is created automatically. A lead without sufficient identity remains linked to a
null Contact and has CONTACT_DATA_INCOMPLETE. Later *new* events can resolve that
link; a retry of the same event does not reprocess it.

Financial data, birth date, gender, offers, raw payload and signature are not stored.
The request is bounded to 64 KiB, including streamed bodies, and only JSON/identity
encoding is accepted. Errors returned are fixed codes, with no raw exception logs.

## Operational limits and rollout

Processing is synchronous with a request-local monotonic eight-second budget.
Body reads, binding lookup and read-only conflict recovery have bounded waits.
Body timeout cancels the reader; budget exhaustion returns sanitized 503.
No new transaction/retry/recovery begins with exhausted budget. Transactions use
up to 500 ms max wait and 1500 ms timeout, capped by remaining budget, with checks
before event persistence and before returning from the callback.
This is NOT cancellation of Prisma queries. A query/transaction/commit already
in flight can finish after the budget; transaction completion is awaited rather
than abandoned with Promise.race. A late commit followed by a 503 is possible:
supplier retry is protected by persisted idempotency. CPU/event-loop stalls and
database commit/network latency prevent an absolute eight/ten-second guarantee.
The supplier's deadline still needs a realistic isolated latency test.
This is not a queue or background worker. Global infra protection remains relevant
because no unauthenticated request rate-limit table writes were added here.

The additive migration creates only these three tables and their constraints, plus
a redundant composite unique index on Contact(companyId,id) needed for tenant-safe
foreign keys. Contact.id is already globally unique; the composite index supports
FK enforcement, and its non-concurrent creation can block Contact writes during
the migration. No existing records are changed. Contact deletion is restricted when
linked: future erasure/retention workflows must explicitly handle that relationship.
Do not apply migrations manually against production for validation.

Before rollout: review migration, prove constraints/concurrent ingestion in disposable
PostgreSQL, review data-retention/erasure and onboarding, then validate normal deploy.
Local Docker was unavailable during implementation; mock tests do not constitute
material PostgreSQL concurrency evidence.

Rollback: disable the integration and revert application changes; retain additive
tables and audit records. Do not drop tables containing operational data automatically.
There is no conversational bridge, controller change or modification of aiProfile.
